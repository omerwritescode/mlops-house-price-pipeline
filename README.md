# House-price MLOps pipeline: raw data to monitored deployment

**MLOps Project 4, Capstone End-to-End MLflow Pipeline.** Group 10 (Sheet 1): **Omer Raza (B052)**,
**Arfeen Khan (B050)**. MSc Data Science, NMIMS. Faculty: Dr. Santosh Kumar.

The pipeline predicts `Price_Lakhs` for property listings. The stages, in order:

1. **Ingest** the data with content hashes, so every dataset has a version.
2. **Validate** it. This is the **data gate**.
3. **Build features**.
4. **Train** with cross-validated grid search.
5. **Evaluate**. This is the **model gate**: the model must meet fixed thresholds *and* beat the
   production model.
6. **Register** the model in MLflow.
7. **Deploy** it with an atomic bundle swap into a FastAPI container.
8. **Monitor** data drift and performance drift on the three incoming batches, using Prometheus,
   Grafana and an HTML report.

All eight stages are orchestrated with Prefect and driven by one YAML file. GitHub Actions runs CI on pull
requests and a release on every merge to `main`.

## Results (deployed model v1, holdout of 787 houses)

| RMSE | MAE | R² | MAPE | within ±10% |
|---|---|---|---|---|
| **7.81** lakhs | **5.84** lakhs | **0.875** | **9.7%** | 58% |

Gate thresholds are RMSE ≤ 9.0, MAE ≤ 7.0, R² ≥ 0.80, MAPE ≤ 15%, and no more than 2% worse than
production. The model is a gradient-boosting pipeline with 600 trees, depth 2 and a learning rate of 0.05.
For comparison, predicting the mean price gives an RMSE of 22.0.

| Incoming batch | Level | RMSE (× holdout) | What drifted |
|---|---|---|---|
| 1 | OK | 7.18 (0.92×) | nothing |
| 2 | WARNING | 9.21 (1.18×) | performance only; under-pricing of 4.5 lakhs (7%) |
| 3 | CRITICAL | 16.24 (2.08×) | Area PSI 0.33, Bedrooms 0.20, City_Zone 0.21, Bathrooms 0.11; under-pricing of 12.8 lakhs (21%) |

Reproduce these numbers with `make verify`: it checks `reports/reference_metrics.json` within ±0.05 lakhs.

## Quickstart

Requires Python 3.11 and Docker for the serving stack.

```bash
git clone <repo-url> && cd mlops-house-price-pipeline
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
make setup        # pip install -r requirements.txt && pip install -e .
make pipeline     # all 8 stages through Prefect (use `make pipeline-local` to skip Prefect)
make verify       # reproduces the reported metrics within tolerance
make up           # API :8000, Prometheus :9090, Pushgateway :9091, Grafana :3000, MLflow UI :5000
make replay       # send the incoming batches through the API to fill the Grafana dashboard
```

On Windows without `make`, run the command shown inside each Makefile target. For example, `make pipeline`
is `hpp run`.

## Commands

| Command | Does |
|---|---|
| `hpp run` | full pipeline (`--engine local\|prefect`, `--until <stage>`, `--skip-monitor`, `--batch-file f.csv`, `--override overlay.yaml`, `--train-with-batches 1,2`) |
| `hpp stage <name>` | re-run one stage from its declared inputs (`make stage S=train`) |
| `hpp retrain --batches 1,2,3` | retrain on train data plus the labelled batches; the same gates apply |
| `hpp monitor [--batches 3] [--file x.csv] [--api-url …]` | drift and performance report, pushed to Pushgateway when configured |
| `hpp lineage [--api-url …]` | trace the deployed model to its registry version, MLflow run, commit, data hash and config hash |
| `hpp rollback` | restore the previous bundle and registry aliases |
| `hpp history` | stage-level run history from `logs/run_history.jsonl` |
| `hpp validate-config` | strict validation of the config and its overlays |
| `make failures` | the three failing-gate scenarios, written to `docs/evidence/failure_scenarios.md` |
| `make rollback-test` | retrain, deploy, roll back, check the restored bundle is identical; written to `docs/evidence/rollback_test.md` |
| `make evidence` | regenerate everything in `docs/evidence/` from a clean state |
| `make test`, `make lint` | pytest (unit, integration, API) and ruff |

Exit codes: `0` ok, `2` data gate failed, `3` model gate failed, `4` invalid config, `5` missing stage
input, `6` metrics not reproduced.

To see runs in the Prefect UI, start the server (`make prefect-ui` or
`docker compose --profile prefect up -d prefect`), then
`export PREFECT_API_URL=http://localhost:4200/api` before `make pipeline`.

## How each task is met

| Task | Where |
|---|---|
| **1 Design** | `docs/design_note.md`: objective, metrics in plain language, NFRs, retrain policy, every threshold justified with numbers, architecture diagram (`docs/make_diagrams.py`), lifecycle table |
| **2 Reproducibility** | `configs/config.yaml` is the single source of truth. Strict pydantic validation (`hpp.config`) accepts `${ENV:-default}` and overlays. Data is versioned by sha256 (`data_version`), the config by its hash, the code by commit. Dependencies are pinned in `requirements.txt`. The holdout is a deterministic hash split. `make verify` reproduces the reference metrics from a fresh clone. |
| **3 Orchestration** | `hpp.orchestration` runs the Prefect flow `house-price-pipeline`, one task per stage. `STAGE_IO` declares each stage's contract, so any stage can be re-run alone. Logs go to `logs/<run>/<stage>.log` and history to `logs/run_history.jsonl`. Graph: `docs/workflow_graph.md`. |
| **4 Gates** | Data gate: `hpp.validation`, checked per source. Model gate: `hpp.evaluate`, thresholds plus comparison with production. Both raise typed errors, print a "stopped safely" banner and leave production untouched. Three scenarios in `docs/evidence/failure_scenarios.md`: bad batch, weak model, regressed model. |
| **5 Tracking and registry** | `hpp.tracking`: MLflow runs (params, metrics, artifacts, signature, lineage tags), model `house-price-model`, aliases `candidate`, `production` and `previous-production`. Aliases are set only by the pipeline, tagged `transitioned_by=pipeline`, and audited by `hpp lineage`. |
| **6 CI/CD** | `.github/workflows/ci.yml`: PRs get ruff, config validation, pytest, a light pipeline (`configs/ci.yaml`) and an image smoke test. `release.yml`: a merge to `main` runs the full pipeline and the reproducibility check, builds the image `ghcr.io/<owner>/hpp-api:sha-<commit>` (also `v1.0.<run>` and `latest`), smoke-tests it by checking `/version` returns the commit, pushes it and creates a GitHub release. `rollback.yml` and `docs/rollback.md` cover rollback, tested in `docs/evidence/rollback_test.md`. |
| **7 Deployment and monitoring** | `Dockerfile` with FastAPI `hpp.serving.app` (`/predict`, `/predict/batch`, `/health`, `/version`, `/model-info`, `/metrics`). Prometheus metrics cover latency, throughput, errors and predicted price. Grafana dashboard: `monitoring/grafana/dashboards/hpp.json`. Alert rules: `monitoring/prometheus/alerts.yml`. `hpp.monitor` produces PSI/KS/χ² data drift, RMSE ratio and bias performance drift, and recommends an action for each level. |
| **8 Demo** | `docs/demo_script.md`, with parts for each member |


`deployments/`, `reports/monitoring/`, and `data/scenarios/` (the derived bad batch for the Task 4 demo,
kept separate from the supplied data).

## Notes

- `House_ID` and `Batch` are never used as features: `data.non_predictive` in the config.
- The derived bad batch is generated, not hand-edited: `hpp make-bad-batch`. It is derived from batch 1
  and stored separately.
- The numbers above came from a development environment running Python 3.13 and scikit-learn 1.9. After
  `make setup` in the pinned environment (Python 3.11, scikit-learn 1.5.2), run `make pipeline` and then
  `make reference` once, and commit `reports/reference_metrics.json`. Small differences between
  library versions are expected, which is why the reference is recorded.
- Before pushing to GitHub, replace `OWNER` in the `Dockerfile` label (`org.opencontainers.image.source`).
